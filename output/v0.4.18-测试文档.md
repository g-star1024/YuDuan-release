# 御端 v0.4.18 测试文档 —— 远控指令 TimeSkew 根因修复（第十轮）

## 1. 背景：现场"一直转圈"的完整定位过程（2026-11-04 15:25–16:10）

用户现场：v0.4.17 主端（Mac，已确认二进制含看门狗文案、sample 报 Version 0.4.17）连 v0.4.17 副端（DESKTOP-2TH64T7），远控窗口无限转圈，状态条 `relay · 0 fps · 丢包 0%`，遮罩文案 `requesting: 等待被控端就绪`。

### 1.1 实测证据链（开发方逐条实验）

| # | 实验 | 结果 | 结论 |
|---|---|---|---|
| 1 | 中枢 API 查设备 | `agent_version 0.4.17, online: true`，心跳实时 | 副端在线且是最新版 |
| 2 | Python 直连实测一次远控（envelope `ts`=**秒**） | `rc_ready` 0.28s、首帧 1.46s、45s 655 帧满帧 | 链路与副端完全健康 |
| 3 | 审计日志还原用户操作 | 15:25–15:27 五次会话 1–10s 即"主端请求结束"，15:27:33 最后一次 `rc_start` 后**无 rc_end** | 主端反复重试均失败 |
| 4 | 并发会话实验（A 保持 + B 新开，envelope `ts`=**毫秒**） | B 收到 `rc_event kind=error message="远控指令被拒（时间窗超限）"` | ★ 直接复现并捕获副端拒绝 |
| 5 | 追码三端 | 主端发 ts=**毫秒**（`now_ms()`）→ hub `NormalizeForSigning` **只补 0 值不重打单位**原样转发 → 副端 `verify_command` 按秒判 ±300s 窗 → 毫秒 ts 必然 `TimeSkew` | ★★★ 根因坐实 |

### 1.2 根因结论（对第九轮报告与 v0.4.17"根因修正"的再修正）

- **真根因**：主端 envelope `ts` 用毫秒、副端验签按秒判窗。**仅在部署配置了 HMAC 密钥的生产网触发**（开发态密钥为空 = NoSecret 全放行，故 e2e 与早期测试全绿，掩盖至今）。
- 触发条件闭环：第九轮部署起 `register-task.ps1` 配置了 `YUDUAN_HMAC_SECRET` → 主端所有 rc_* 指令（rc_request/rc_select/rc_input/rc_stop/rc_ping…）全部被副端拒绝 → 永远等不到 `rc_ready` → 无限转圈。
- **勘误**：v0.4.17 测试文档 §2.1 的"根因修正"（传输层无罪、P2P 正常）实验本身有效但**结论不完整**——当时复刻脚本恰好发秒级 ts 所以通过，漏掉了 ts 单位这一真因。第九轮报告"缺陷A：跨机远控失败"的现象是真实的，归因（副端仅绑回环/P2P 不可达）错误，本版一并修正。
- 副端其实**每次都回了明确的错误事件**（`远控指令被拒（时间窗超限）`），但主端 UI 的 `rc-event` 监听没有 `kind=error` 分支，被静默丢弃——用户只看到转圈，看不到原因。

## 2. 本版修复（三端四层）

| 层 | 文件 | 修复 | 效果 |
|---|---|---|---|
| 主端 | `main/src-tauri/src/media_session.rs` | envelope `ts` 全部改**秒级**（新增 `now_secs()`，8 处信封 + rc_stop 路径）；`msg_id` 保留毫秒唯一性；rc_chat payload ts 不受影响 | 协议口径正确，新主端在旧中枢+新副端下直接工作 |
| 主端 | `main/src-tauri/src/p2p.rs` | `envelope()` ts 改秒级 | rc_offer/rc_candidate 同口径 |
| 主端 | `main/src-tauri/src/media_session.rs` | 看门狗退出与"被控端拒绝"路径**补发 rc_stop** | 中枢审计闭环（此前挂"进行中"无 rc_end） |
| 主端 | `main/src/viewer.tsx` | `rc-event kind=error` 透出到状态条 | 副端拒绝原因用户可见，不再静默转圈 |
| 副端 | `rust/agent/src/secure.rs` | `verify_command` 窗口判定**按量级归一 ts**（>1e12 视为毫秒 ÷1000）；签名规范串仍用原始 ts（与中枢 SignCommand 口径一致） | 容忍存量毫秒 ts 客户端 |
| 参考副端 | `dev/internal/crypto/crypto.go` | `VerifyCommand` 同口径归一（Go/Rust 铁律同步） | 两副端口径一致 |
| 中枢 | `dev/internal/proto/util.go` | `NormalizeForSigning` 对**窗口外 ts 重打为当前秒**（±300s 内保持原值，防重放语义不变） | 存量旧主端**不升级也被治好**（hub 兜底） |

## 5. 第十一轮实机验收指引（按优先级）

1. **★核心：主端连副端出画面**——v0.4.18 主端直接点远控，预期 2s 内出画面（auto 模式 P2P 直连或 5s 内自动回落中继）。**注意：中枢必须先升级到 v0.4.18**（hub 兜底重打 ts 是旧主端被治好的前提；新主端单升也能工作，但建议 hub+副端+主端三件套一起升）。
2. **拒绝可见性**：临时把副端密钥配错（或停副端）再发起远控，预期 15s 内状态条出现明确错误（不再无限转圈），审计有 rc_end。
3. **审计闭环**：任意方式结束会话（含看门狗超时退出），审计应出现 `rc_end`，不再有悬挂会话。
4. **回归**：敏感设备二次审批全链路（审批期间看门狗重置）、文件拉取（W2-1）、消息（rc_chat）不受 ts 变更影响。
