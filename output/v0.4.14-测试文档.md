### 本版变更摘要

| # | 问题来源 | 修复内容 |
|---|---|---|
| 1 | v0.4.13 报告 ①meta 整行覆盖 | `/devices/meta/{id}` 改为**部分更新**：只更新请求中出现的字段，未提交字段保持原值。前端不再需要携完整台账（`api.ts` 已同步简化）。审计日志记录实际变更字段列表 |
| 2 | v0.4.13 报告 ②viewer 可写台账 | meta 写操作服务端强制 `device:cmd`：viewer 提交返回 **HTTP 403 / code=4003**（此前仅靠前端隐藏入口，RBAC-1 越权已堵）。GET 查询仍开放 device:view |
| 3 | v0.4.13 报告 ③就绪行早于登录 | 中枢就绪行改为**回环 HTTP 登录探针**：真实 `POST /api/v1/login`（200/401 均算 HTTP 就绪），不再依赖进程内状态。`register-task.ps1` 自检③重试 7→20 次（约 60s），规避旧实例占端口误判 |
| 4 | v0.4.13 报告 ④远控合成彩虹帧 | ⚠️ **本版未生效，顺延 v0.4.15**：双进程真实抓屏（`rc_windows.go`+`rc_helper_windows.go`）实现于 Go 开发实现 `dev/cmd/agent`，但发版核验发现**发布副端实际由 `rust/agent` 构建**（CI release-build.yml 全平台副端均 rustc 构建，二进制 sha256 核验无 `--rc-helper`/WTS 符号）。Rust 副端自 v0.4.11 起未改动，Windows 下仍以 SCM 服务（Session 0）直接 `GetDC(null)`+BitBlt 抓屏——Session 0 拿不到用户桌面画面，即实测 0 帧的真正根因，**本版 Windows 副端远控行为与 v0.4.13 相同** |
| 5 | 10 张实测截图 | 主端 UI 逐项治理：相对时间 Go 零值防护（不再出现「739922 天前」）、分段控件样式、select 自绘箭头、表格头间距、长值换行、viewer 遮罩可读性等（详见 §4.5） |

## 2. 环境准备

1. 下载并部署 **YuDuan-hub_v0.4.14_windows_amd64.zip**。启动后确认日志出现「内置 admin 账号就绪」再开始测试——本版该行语义已改为回环 HTTP 真实探针，出现即代表可登录。
2. **Agent-A**（关键测试机）：卸载旧副端后安装 **YuDuan-agent_v0.4.14_windows.exe** 并注册。保持**已登录桌面会话、不锁屏**。
3. **Agent-B**：同版本安装注册，用于多设备回归。
4. 主端安装 **YuDuan-console_v0.4.14_windows_x64.exe**（macOS 用对应 dmg）。
5. 建议先跑一次 `cleanup.ps1`（v0.4.9+ 附带）清理旧实例，避免旧 hub 占用 8080 造成就绪探针误导。

## 3. 新功能测试用例

### 3.1 Windows 远控（本版**不测**，顺延 v0.4.15）

⚠️ 本版 Windows 副端未含双进程抓屏修复，远控行为与 v0.4.13 相同（Session 0 直抓，预期仍 0 帧/黑屏）。**请勿在本版投入远控测试时间**，该用例集整体顺延至 v0.4.15（Rust 副端双进程修复版）：

| 步骤 | 操作 | 预期（v0.4.15） |
|---|---|---|
| 1 | 主端→设备→对 Agent-A 发起远控 | viewer 显示真实桌面画面（助手进程 `--rc-helper` 在用户会话内 BitBlt 抓屏） |
| 2 | 鼠标移动/点击、键盘输入 | Agent-A 桌面实际响应 |
| 3 | **锁屏 Agent-A** 后再次发起远控 | viewer 显示明确失败原因，副端日志带原因 |
| 4 | （回归）macOS/Linux 副端远控 | 行为不变 |

### 3.2 设备台账部分更新

| 步骤 | 操作 | 预期 |
|---|---|---|
| 1 | 设备详情中**只修改「部门」**并保存 | 保存成功；重新打开详情，**楼层/批次/标签/敏感状态等全部保持原值**（v0.4.13 前会被清空） |
| 2 | 修改「楼层」保存 | 部门与其他字段仍保持 |
| 3 | 切换「敏感」开关保存 | 其余字段保持；敏感状态生效（走 W2-4 二级审批闭环） |
| 4 | 中枢审计日志 | 每次保存记录**实际变更的字段名列表**（如 `department`），而非整行 |
| 5 | PG 版中枢（如部署） | 行为与内存版一致 |

### 3.3 viewer 写权限（RBAC）

| 步骤 | 操作 | 预期 |
|---|---|---|
| 1 | 用 **viewer** 账号登录主端 | 设备详情台账面板为只读（前端无保存入口，与 v0.4.13 一致） |
| 2 | （API 层验证，可选）viewer 会话直接 POST `/api/v1/devices/meta/{id}` | 返回 **403**，body `code=4003`（服务端强拦，即使绕过前端也无法越权） |
| 3 | **operator** 账号修改台账 | 正常 200 保存成功 |
| 4 | viewer 查看设备列表/详情 | 正常（device:view 未收紧） |

### 3.4 中枢就绪行时序

| 步骤 | 操作 | 预期 |
|---|---|---|
| 1 | 全新机器按指引 `register-task.ps1` 部署 | 自检③「等待中枢可登录」最多 60s 内通过 |
| 2 | 观察服务日志就绪行出现时机 | 就绪行出现后**立即**用浏览器登录 hub，应当直接成功（不再出现「就绪但登录 401」窗口期） |
| 3 | 旧实例占用 8080 场景（可选） | 启动失败并有明确端口冲突提示，不误报就绪 |

## 5. 已知限制 / 观察点

| # | 项 | 说明 |
|---|---|---|
| 1 | **Windows 副端远控未修复** | 双进程抓屏修复误落 Go 开发实现（`dev/cmd/agent`），发布副端为 `rust/agent`（Session 0 直抓）。根因分析与修复方案已明确，v0.4.15 将在 Rust 副端落地同方案（服务 WTS 拉起用户会话助手 → 助手内 GDI 抓屏 + SendInput 注入 → 回环中继） |
| 2 | O-1 meta 守卫观察点 | 本版已部分收口：写操作强制 `device:cmd`。是否将其提为正式 RBAC 矩阵变更待拍板 |
| 3 | Linux arm64 副端 | 仍延后（GitHub runner 多架构镜像版本偏移），见 v0.4.12 说明 |
