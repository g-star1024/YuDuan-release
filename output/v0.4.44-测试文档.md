## 1. 变更摘要

| 报告项 | 级别 | 本版落点 |
|---|---|---|
| **N2/V3 回归失败**（1052 依旧、PID 不变、重装 93s） | 高（P0） | **真根因四层全剥（CI 探针实锤）**：L3 accept 位错（0x2/0x80，官方 0x1/0x4）→ STOP 位未开放必 1052；L4 控制码错（STOP 误写 0、SHUTDOWN 误写 0x8，官方 0x1/0x5）→ SCM 投递 control=1 但 match 不命中。改对全部常量 + 单测锁值 + STOP 分支重排纵深冗余 + **CI 级 sc stop ≤5s 断言（本轮已绿）** + 服务内探针保留 |
| **N6** initdb 不支持非 ASCII 安装目录（N1 的下一层） | 高（P1） | 按报告方案①+③：便携 PG 根目录 `$PgHome` 与安装目录解耦——安装目录纯 ASCII 沿用旧路径（零行为变化）；否则 `%ProgramData%\yuduan-pg`（再退 `%SystemDrive%\yuduan-pg`）；两者皆非 ASCII 才以 `PG_PATH_NONASCII` 早失败 |
| **N8** main.log 创建后 0 字节 | 中（P2） | 真根因：Windows GUI 子系统（windows_subsystem="windows"）下 `GetStdHandle` 为 NULL，Rust std 的 println!/eprintln! 静默丢弃；v0.4.40 的 CRT 层 dup2 管不到。修复：`SetStdHandle(STD_OUTPUT/ERROR_HANDLE, 日志句柄)` + 启动横幅写日志（双端），日志恒非空、验收有锚点 |
| **N7** 云端部署 >25min 阶段不可观测 | 中（P2） | 部署器新增 `Write-Stage`：下载开始/结束、解压完成、initdb、PG 就绪、自检通过等里程碑行统一 ` HH:mm:ss` 时间戳 |

| **N9** offline-bundle 判定缺失 | 低 | 测试台编排问题（state 文件 `_run` 判据），无代码改动 |

## 2. V3/N2 真根因裁决（关键——最终为**四层洋葱**）

裁决链（现象始终为真，归因逐层修正；每层都有 CI 探针/实证背书）：

| 层 | 归因 | 证据/结果 |
|---|---|---|
| L1（v0.4.40 修复） | 「handle_ex 只报 STOP_PENDING 且主循环阻塞」→ 改为立即报 STOPPED | 不成立：1052 是 SCM 侧拒收，控制码根本没到 handler |
| L2（v0.4.41 修复） | 「service_main 同步阻塞占满 dispatcher 线程」→ 主逻辑 spawn 独立线程 | 方向合理（必要条件）但非主因：1052 与线程模型无关 |
| **L3（v0.4.44）** | **accept 位常量错**：STOP=0x1/SHUTDOWN=0x4 写成 0x2/0x80 → RUNNING 上报 0x82（PAUSE\|SESSION）→ STOP 位未开放 → `sc stop` 必 1052 | 修复后 CI 实证 `sc stop` exit=0（1052 消失） |
| **L4（v0.4.44 CI 第 5 轮实锤）** | **控制码常量也错**：`SERVICE_CONTROL_STOP` 官方 **0x1**（误写 0=无效码）、`SERVICE_CONTROL_SHUTDOWN` 官方 **0x5**（误写 0x8=NETBINDREMOVE）→ SCM 正确投递 control=1，match 按 0 匹配不命中 → 服务永不停止 | 服务内探针 svc-trace 实锤：`handle_ex control=1 received` 后零后续 trace；修复后 **CI V3 断言绿**（sc stop 5s 内 STOPPED） |

**为什么此前一直没暴露**：控制码 210（用户自定义区 128-255）不受 accept 位约束且**恰好写对** → V1 热切换一直正常，同时掩盖了 L3 与 L4；`sc query` 显示 Running 正常（RUNNING 上报本身成功）。L4 修复同时把 STOP 分支重排为「先置停止标志+打断会话、最后 report」——即使 SetServiceStatus 意外阻塞，工作线程也先退出、进程退出时 SCM 自动标 STOPPED（纵深冗余）。

**证据**：MSDN HandlerEx / SERVICE_STATUS 官方值；CI 探针日志（`C:\ProgramData\yuduan-svc-trace.log` 经 ci-logs-win 孤儿分支带回）；V1（210 正常）+ V3（1052→受理→不停止→修复后 5s 内 STOPPED）现象组合完全吻合。

**防再犯三保险**：
1. 单测 `service_accept_bits_match_winsvc_h` 锁死 accept 位 0x1/0x4、掩码 0x5 **及控制码 0x1/0x5**；
2. **CI 级断言**（build-windows 每轮强制步）：runner 上以服务方式拉起刚构建的 `yuduan-agent.exe`，`sc stop` 必须 5s 内转 STOPPED，否则构建失败——报告「建议加一条 CI 级断言而不是继续靠文档」已落地；
3. 服务内 `svc_trace` 探针保留（best-effort 落 `C:\ProgramData\yuduan-svc-trace.log`），实机排障可直接取证。

## 6. 边界说明

- V10a 未改默认行为：LAN 下自动信任 XFF 会被本机进程伪造（审计可信度权衡），维持「公网/-Public 显式开启」+ 摘要提示。如需更强自动性可后续评估「仅 loopback 对端且 XFF 存在时采信」的折中。

- CI V3 断言步每轮发版强制执行（非门控）——它现在就是 V3 的验收记录。

## 7. 结论

第 24 轮报告的 6 个发现全部处置：V3 找到并修复了跨越三轮、共四层的真根因（accept 位常量 + STOP/SHUTDOWN 控制码常量），N6 按「方案①彻底解耦」落地并保留 ASCII 路径零行为变化，N8 修在 Rust std 句柄层而非 CRT 层，N7/V10a 补观测性，N9 属测试台编排（无代码改动）。V3 从此有 CI 级断言背书（本轮已绿）+ 服务内探针（`C:\ProgramData\yuduan-svc-trace.log`）实机排障取证。
