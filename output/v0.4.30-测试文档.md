## 4. 发布仓 CI 复核结论（含致命 parse 失败复盘）

### 4.1 致命缺陷：step `if:` 引用 `secrets` 上下文 → 整份 workflow 解析失败
- **现象**：首次打 `v0.4.30` tag 触发两条 run（`42476103720` / `42476099041`，head `2e3deb3`）**同时 `completed/failure` 且 0 jobs**，创建与结束时间戳同一秒（`11:31:13Z`）——典型「workflow 无法解析、从未派发 runner」。对照 v0.4.29 同口径 `42453134773` 返回 **7 jobs**，证明非 API 鉴权问题。
- **根因（GitHub Actions 硬限制）**：**`secrets` 上下文不允许出现在 step `if:` 表达式里**（安全限制，防 secret 泄漏到日志）。初版 signtool 步骤写 `if: ${{ secrets.WIN_CODESIGN_PFX != '' }}` → 整份 YAML 被拒（`Invalid workflow file`，Line 387 Col 13：`Unrecognized named-value: 'secrets'`）。
- **为何本地校验没抓到**：PyYAML `safe_load` 只校验 YAML 语法，不校验 GitHub Actions 表达式上下文可用性；`secrets` 在 `if:` 是语义层拒绝。已补「全仓 `grep 'if:.*\$\{\{.*secrets'`」检查。
- **修复**：删除该 `if:`，改为 pwsh 脚本体内判定（缺 `WIN_CODESIGN_PFX` → `::warning::` 跳过 + `exit 0`），与上方 osslsigncode 块（bash 脚本体内 `if [ -n "${WIN_CODESIGN_PFX:-}" ]`）保持同一门控范式。**`secrets` 仅出现在 `env:` 映射里（合法）**，绝不出现在 `if:`。

### 4.2 越界与语义复核（修复版 `21c9f6a`）
- **A 静态**：YAML 解析 7 jobs、结构校验无异常、无重复键；两签名块均「缺证书 = 无操作 + 警告」，证书存在时再签。
- **B 越界**：仅 release-build.yml 改动；既有 `GITHUB_REF_NAME` / publish 结构 / server-db `cp -r` 链路全未动。
- **C 语义**：osslsigncode 段（Ubuntu，签 Go 三 exe）与 signtool 段（Windows，签 agent+main，RFC3161 时间戳）分工清晰；无证书时两段均为 no-op，开源构建零回归。

## 6. 技术债与限制

1. **门控签名尚未真签**：当前开源构建无证书，四/五 Windows exe 仍**无 Authenticode 签名**（仅 rcedit/goversioninfo 写版本资源）。用户配置 `WIN_CODESIGN_PFX`(base64)/`WIN_CODESIGN_PWD` Secret 后，下版 CI 自动签名；签名须放在 rcedit 之后（已在 v0.4.29 技术债登记）。
2. **O-02 仅静态审查**：`deploy.bat` 透传逻辑本机无 Windows 环境未实跑，需 Windows 实机双击确认「问 UDP 发现端口 → 透传 `-DiscoveryPort` → hub.env 写入」闭环。
3. **PG 失败即中止仅静态审查**：三脚本门控本机无 pwsh/无 Linux 部署环境未实跑，需三平台实机各跑一遍确认中止文案与逃生舱。
4. **历史草稿排除**：`dev/cmd/agent/wave3.go`（M）、`dev/cmd/agent/wave3_https_test.go`（??）、根目录散落 zip/ps1、`output/` 一律不进 v0.4.30 tag（避免 `go test ./...` 编译失败）。
5. **workflow_dispatch 补发包名漂移**：既有 11 处裸用 `GITHUB_REF_NAME` 未兜底，dispatch 留空 `source_ref` 会写 "main" 版本串/包名；属既有缺陷、非本版引入，正式 tag 触发不受影响。
6. **CI `if:` 禁 `secrets` 已固化为铁律**：所有「按 Secret 是否存在决定是否执行步骤」的场景，一律改在脚本体内判定，绝不用 `if: ${{ secrets.X }}`（本次血泪教训，已补 grep 检查）。
