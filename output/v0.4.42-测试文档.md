## 2. 根因审计（N5 失败路径本来就是对的）

**报告 N5 原文**：「本轮矩阵未含 offline-nobundle 用例，`PG_INSTALL_FAILED` 路径与 600s 上限的实际表现仍待一次专项验证」。

**审计结论**：失败路径在 v0.4.40 已实现且正确，无需「修」，只需「验」+ 一处体验加固。

`dev/deploy/hub/register-task.ps1` `Install-OwnPg` + `Install-PortablePg`（v0.4.40 落点）失败闭环：

| 失败点 | 代码位置 | 行为 |
|---|---|---|
| 下载失败（无公网/超时） | `Install-OwnPg` 下载 `curl -m 600` 后 `if ($dlExit -ne 0 …)` → `$script:DeployReason="PG_INSTALL_FAILED"`（line 463） | 置结构化原因码，返回 `$null` |
| 解压缺 `initdb.exe`（zip 异常/下载不完整） | `Install-OwnPg` 末段 `Test-Path` 失败 → `PG_INSTALL_FAILED`（line 480） | 同上 |
| `Start-OwnPg` 失败（initdb/服务起不来） | `Install-PortablePg` `if ($bin -and -not (Start-OwnPg …))` → `PG_INSTALL_FAILED`（line 569） | 同上 |
| 兜底聚合 | `--NonInteractive` 且无 DSN → `Fail-Deploy -Reason $reason`（`$reason = $script:DeployReason -ne "OK" ? DeployReason : "DSN_MISSING"`，line 638） | 不会把根因误报成 `DSN_MISSING` |

**600s 上限**：下载 `curl … -m 600`（line 457）是绝对上限；`--connect-timeout 15 --retry 3` 控制单次连接。即：明确的「无路由/无法解析」网络会在 connect-timeout 内快速失败；「黑洞网络」（静默丢包）最多等 600s 后超时失败——**不会无限挂死**。

**因此 N5 的「修复」不是补缺失逻辑，而是让离线场景失败得更快、更确定**，并给出可在 Windows 测试机上复现的专项验证程序（§6）。

## 3. 本次加固（offline-nobundle 快速失败）

新增下载前 10s 可达性预探（`register-task.ps1` `Install-OwnPg` 下载分支顶部）：

```powershell
# v0.4.42（N5）：offline-nobundle 快速失败——在重 600s 下载前，先用极短超时探一次
#   PG 主机可达性。curl 明确"无法解析/无法连接"（exit 6/7，对应无公网 DNS 失败或路由
#   不通）即判定离线，跳过 600s 下载直接置 PG_INSTALL_FAILED 快速返回（离线机不空等 10 分钟）。
#   其余情况（含超时 exit 28 黑洞网络）一律放行走原逻辑真实下载（受 -m 600 约束），
#   绝不因探活失败而抑制一次本可成功的下载（零误杀）。
$probeExit = (& curl.exe -s -m 10 -o NUL -I "$PG_URL")
$pe = $LASTEXITCODE
if ($pe -eq 6 -or $pe -eq 7) {
  $script:DeployReason = "PG_INSTALL_FAILED"
  Write-Host "[WARN] PostgreSQL 主机不可达（curl exit=$pe，疑似无公网/离线），跳过下载直接失败。" -ForegroundColor Yellow
  return $null
}
```

设计要点（零误杀）：
- **仅 exit 6（无法解析）/ 7（无法连接）短路** —— 这两种是「明确离线」信号，主机不可能在本 10s 内变可达。
- **exit 28（超时/黑洞）、网络瞬断、HEAD 被拒（405，exit 0）一律放行走原 600s 真实下载** —— 绝不因一次预探失败而抑制可成功的下载。
- 预探用 `HEAD`（`-I`）+ `-m 10`，对 EDB 静态 CDN 无副作用；即便 HEAD 返回 405，curl 仍 exit 0 → 放行下载。
- 不引入新依赖、不改既有成功路径（有本地 bundle / 有公网下载仍按原逻辑）。

## 6. N5 专项验证程序（待用户 Windows 测试机复测）

**场景**：一台**无公网**且**未放离线 PG 包**的干净 Windows 服务器，跑一键部署，验证失败路径按预期快速/有界失败并给出结构化原因码。

**步骤**：
1. 断网（或防火墙阻断 `get.enterprisedb.com`），确认安装目录及父目录下**没有**任何 `pgsql-*-binaries.zip`。
2. 以 `--NonInteractive` 跑 `register-task.ps1`（或一键部署入口）。
3. 观察：
   - **快速失败分支（明确离线，DNS 失败/路由不通）**：约 10s 内出现 `[WARN] PostgreSQL 主机不可达（curl exit=6/7 …）` → 直接 `PG_INSTALL_FAILED` 返回，**不空等 600s**。
   - **黑洞网络（静默丢包）**：走到原 600s 下载，超时后报 `PG_INSTALL_FAILED`，**总等待 ≤600s，不无限挂死**。
4. 断言 `deploy-result.json`：`{ "success": false, "reason": "PG_INSTALL_FAILED", … }`（非 `DSN_MISSING` —— 验证根因未被聚合误报）。
5. 确认中枢**未以内存模式静默启动**（`--NonInteractive` 下 `Fail-Deploy` 中止，退出码非 0）。

**对照基线（v0.4.40 已实测通过的部分）**：V9 进度输出「[下载] curl 结束（exit=0）：已下载 314500604 字节 / 耗时 1.045140s」、`-m 600` 上限生效；本次只补「失败分支」的确定性验证。
