## 2. 根因裁决（源码级铁证）

### 2.1 N2（P2-5 复现核查）—— 真根因是 SCM 线程模型，v0.4.40 改在了但走不到

**报告质疑**：v0.4.40 已把 `handle_ex` 改为「立即上报 STOPPED」，实机行为却未变（`sc stop` 后仍 Running、PID 不变）。是否改动没进构建产物？

**裁决：改动进了产物，但永远执行不到。** 根因在 `service_main` 的线程模型，不在 `handle_ex` 内容：

- `StartServiceCtrlDispatcherW` 在调用 `service_main` 的**同一线程**上阻塞并派发控制码（STOP/SHUTDOWN/自定义 210）。
- v0.4.40 的 `service_main` **同步阻塞**在 `f()`（即 `run_agent_loop`）直到服务退出——派发线程被主循环占满，`HandlerEx` 永远等不到被 SCM 派发。于是 `sc stop` 的 STOP 石沉大海，服务卡 RUNNING、PID 不变（v0.4.40 实测 10s 仍 Running）。
- 因此 v0.4.40 在 `handle_ex` 里写的「立即 report(SERVICE_STOPPED) + interrupt_active_session()」是**正确但不可达**的代码——这正是「现象真（不生效）、归因错（以为是改动缺失）」的又一次重演。

**修复设计（线程模型层修正）**：
```rust
// win_service.rs service_main（v0.4.41）
// 服务主逻辑 MUST 在独立线程运行，service_main 立即返回，
// 交还 StartServiceCtrlDispatcherW 的派发线程——否则该线程被 run_agent_loop
// 阻塞，HandlerEx(STOP/SHUTDOWN/210) 永远等不到被派发，sc stop 石沉大海。
let f = SERVICE_MAIN.lock().unwrap_or_else(|p| p.into_inner()).take();
if let Some(f) = f {
    let _ = std::thread::Builder::new()
        .name("agent-svc-main".into())
        .spawn(move || { f(); });
}
// service_main 返回即交还派发线程；控制码由 HandlerEx 在 dispatcher 线程处理，
// 此处不再 report STOPPED（交由 HandlerEx 的 STOP 分支，避免重复/竞争上报）。
```
配套既有逻辑（v0.4.40 已写、本次始可达）：`handle_ex` 收到 STOP/SHUTDOWN 立即 `report(SERVICE_STOPPED)` + `interrupt_active_session()` 打断在线会话；`STOPPED_REPORTED` 单调保护防重复上报；`sleep()` 250ms 轮询打断。现在因线程模型修正，这些分支**真正可达**，V3（sc stop 5s 内 STOPPED、PID 变化）应随本次通过。

**预期回收**：V3 `sc stop` 5s 内 STOPPED、PID 变化；两轮重装 P95 <30s（卸载清端点 + 重装）。

### 2.2 N1 —— 中文路径代码页错配

`register-task.ps1` v0.4.40 的 `Install-OwnPg` 解压走 `cmd /c tar -xf <zip> -C <CJK路径>`：
- `cmd.exe` 默认活动代码页（GBK/936）与 tar/zip 内部 UTF-8 路径名错配 → 非 ASCII 目录名解压挂起（实测 >240s 未完成）；同一命令在 ASCII 路径 68s 内完成。
- **修复**：优先 `[System.IO.Compression.ZipFile]::ExtractToDirectory($PG_BUNDLE, $installDir)`——.NET 走 UTF-16 内部路径，不经 `cmd.exe` 代码页；失败再 `cmd /c tar` / `Expand-Archive` 兜底。并显式打印解压耗时与产物校验，便于区分「死锁」与「极慢」。

### 2.3 N3 —— 公网反代源地址塌缩

`loginGuardClientIP` 默认只信 `r.RemoteAddr`（公网/隧道形态下恒为 127.0.0.1 反代自身）。仅 `YUDUAN_TRUST_PROXY=1` 才采信 `X-Forwarded-For` 首段。CF 隧道 / 反代下不开启则 `source_addr` 塌缩为 127.0.0.1（V10 实测）。
- **修复**：部署器 `-Public` 段（公网/隧道形态）在 `YUDUAN_LOGIN_GUARD` 之后自动 `Set-HubEnvLine $envFile "YUDUAN_TRUST_PROXY" "1"`。XFF 仅反代可写，安全；使台账服务端观测地址可信。

### 2.4 N4 —— 澄清：主端 Windows 是便携裸 exe，非安装程序

`release-build.yml` `build-windows` 主端步骤：`npx tauri build --no-bundle` → 产出 **`yuduan-main.exe` 裸二进制**（注释原文「Build 主端（Windows exe，**免安装器取裸 exe**）」），无 NSIS/Burn bundle，自然不存在 `/quiet` 静默参数。
- 报告所谓「安装器弹 GUI」实为直接运行主端 GUI 本身；V7 受阻是「无法无人值守安装/静默验证主端文件日志」，并非代码缺陷。
- **回收方案**（见 §6）：V7 改为「直接运行 `YuDuan-main_v0.4.41_windows.exe` + 验证 `%APPDATA%\YuDuan\logs\main.log` 产出」；后续版本若要企业批量静默分发，再补 NSIS installer（独立任务，不在 v0.4.41）。
