## 一、最重要的结论：主仓上一版根因结论被证伪

主仓 `dd86eab` 与 `dev/verify-windows-report-20261025.md` 把栈溢出归因于
**「rustc 1.98.1 旧工具链缺陷」**，并据此加了「rustc minor ≥ 99」的工具链断言。

**这个结论是错的。** 本次拿到的 `(2).zip` 就是主仓按该结论重编的产物：

| 校验项 | 主仓断言 | 实测 |
|---|---|---|
| 内嵌 rustc commit | 应为 1.99.1 | ✅ 确为 `58cf8f9c35b3`（1.99.1） |
| 工具链断言 | minor ≥ 99 应通过 | ✅ 确实通过 |
| **Windows 实机启动** | 预期正常 | ❌ **仍崩，退出码 `0xC00000FD`，零输出** |

**本机原生 rustc 版本 = `1.99.1 (58cf8f9c35b355199727627d07ae34a4e2846d67)`，
与新包内嵌 hash 完全一致 —— 同一版编译器，一个崩一个不崩。**
所以变量不在 rustc 版本上，**版本断言防不住这个问题**。

## 二、真正的根因：交叉编译链本身

崩与不崩的差别是**产物结构**，不是编译器版本。三个产物横向对比：

| 产物 | 大小 | section | `.tls` 段 | TLS 回调 | `__mingw` | `_Unwind_` | addr2line/gimli | 结果 |
|---|---|---|---|---|---|---|---|---|
| `(2).zip` 新包 | 1,601,024 | **6** | **有** | **2** | **17** | **17** | **81 / 258** | ❌ 崩 |
| 旧包（1.98.1） | 1,554,432 | **6** | **有** | **2** | **17** | **17** | **79 / 245** | ❌ 崩 |
| 本机原生 MSVC | 698,880 | **5** | 无 | **0** | 0 | 0 | 0 / 0 | ✅ 正常 |

**规律非常干净：**
- 两个崩溃产物 = macOS 交叉编译（rust-lld + mingw-w64 CRT + libgcc/gimli 展开器），
  特征是 **有 `.tls` 段 + 有 TLS 回调 + 有 mingw/libgcc 符号**；
- 唯一正常产物 = Windows 原生 MSVC 工具链构建，**无 `.tls` 段、无 TLS 回调、无展开器符号**。

**崩溃发生在 `main()` 之前**（连 `[agent] 防篡改自检` 都没打印），且
`.tls` 回调正是在 `main` 之前由系统加载器调用的 —— 崩溃点与 mingw TLS 初始化路径吻合。

### 崩溃复现证据

```
$ yuduan-agent.exe version
returncode = 0xC00000FD (3221225725)   stdout=0 bytes   stderr=0 bytes
```

连续 3 次冷启动，退出码与输出长度完全一致，**100% 复现、非偶发**。

同时排除干扰项：
- 栈保留/提交：三个产物**均为** reserve=1MB / commit=4KB，无差异；
- 旧包已排除的因素同样适用于新包：`RUST_MIN_STACK=32MB` 无效（无限递归，非大栈帧）；
- 依赖 DLL 全部存在（`bcryptprimitives.dll` / `USERENV.dll` 都在 System32）。

> 新包 exe 依赖表里多了 `bcryptprimitives.dll`、`USERENV.dll`、
> `api-ms-win-crt-private-l1-1-0.dll`，缺 `VCRUNTIME140.dll`、改依赖
> `api-ms-win-crt-locale-l1-1-0.dll` —— 这也是 mingw 与 MSVC CRT 的典型差异，
> 与上面的结构判据互相印证。
